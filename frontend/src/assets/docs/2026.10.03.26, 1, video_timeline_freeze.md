The freeze happens when the playhead moves on a large file, while LosslessCut stays responsive with a separate line marker during fast scrubbing. I’ll compare how this app updates the timeline against that behavior.

The freeze comes from assigning `video.currentTime` on every pointer move, so the decoder works through each intermediate frame. LosslessCut avoids that by moving a triangle playhead immediately and only seeking when the previous frame has finished.

The triangle playhead was being pulled back to the decoded frame. While paused, that position should stay where you dragged it, and only the catch-up line should follow the video.

Dragging the timeline no longer waits for every intermediate frame to decode. The playhead follows the pointer immediately, and the video seeks only to the latest position once the previous frame is ready.

On a large file, each pointer move was setting `video.currentTime`. The decoder then rendered every position along the drag, and the window stopped taking input until that queue finished. LosslessCut avoids this by keeping two markers:

- The marker with triangles at the top and bottom is where you dragged. It moves at once, and the time readout moves with it.
- The plain line is the frame the video has actually decoded. It appears only while that frame is still catching up, then disappears.

**Cursor**

The seek coalescing did not change the delay, so the bottleneck is somewhere else. I’ll compare this app’s scrub path with LosslessCut’s and look for what still runs on every playhead move.

The delay is not in the playhead code. LosslessCut and this app already schedule seeks the same way: the triangle marker moves immediately, and the video element is asked for one frame at a time. Changing that scheduling cannot make the picture appear faster, which is why the last two commits did not change what you see.

LosslessCut points the `<video>` element at the file itself:

```javascript
video.src = pathToFileURL(filePath).href  // file:///C:/Users/.../Meeting Recording.mp4
```

Chromium then reads the file in-process. The sample index is parsed once. A seek is a lookup of a byte offset and a read of that slice.

This app points `<video>` at an HTTP URL, `/media/f1/file.mp4`. Every byte goes through the Wails asset server: `backend/media/media.go` opens the file again with `os.Open` and answers with `http.ServeContent`, and every response is sent with `Cache-Control: no-cache`. The element also uses `preload="auto"`, so the media pipeline tries to pull the file through that same bridge.

On this recording the pictures are cheap to decode. The file is 287MB for 1 hour 43 minutes, about 370 kbps, and a 6-second group of pictures is only a few hundred kilobytes. The expensive part is the index: the `moov` atom sits at the front and is **1.7MB**, one entry per frame. With a `file:///` URL that table stays in the demuxer. Over this HTTP path, a seek has to ask Go for those bytes again before a frame can be shown. That is the pause that feels like every frame is being processed.

The catch-up line only reports that wait. It cannot shorten it. The preview will match LosslessCut when the video element can read the file the way LosslessCut’s does, by random access on the path, instead of through a no-cache HTTP handler.

**Cursor**

`file://` from this page is blocked, but that does not mean the app has to move to Electron. I’ll check what WebView2 and this Wails setup can already do for direct file reads.

This can stay a Go application. WebView2 can give the video element the same kind of direct read LosslessCut gets from `file:///`, and the UI can keep being served by Wails.

A `file:///` address on the `<video>` element will not work from this window. The page is loaded from Wails’ own origin (`wails.localhost`), and Chromium refuses `file:///` media from that origin. LosslessCut can use `file:///` because the Electron renderer is allowed to touch the disk. That privilege is the difference, not the language the shell is written in.

Two ways to get that read path without leaving Go:

- **A normal loopback file server in this process.** Listen on `127.0.0.1` with `net/http`, serve the opened file with range requests, and set the video `src` to that URL. Those requests use Chromium’s ordinary HTTP stack. They do not pass through the Wails asset callback that currently opens the file in Go and marks every response `Cache-Control: no-cache`. This is the smaller change in the current app.
- **WebView2’s folder mapping.** `SetVirtualHostNameToFolderMapping` tells the WebView2 runtime to read a folder itself, so a URL like `https://media.local/recording.mp4` is served inside the webview, not by the Go asset handler. Wails 2.12 does not wrap that call, so it means taking the WebView2 controller after startup and mapping the folder that contains the opened file. That is the closer match to `file:///`.

Either one stays in this codebase. Electron would only be required if the app needed Electron’s renderer privileges specifically, and it does not.

**Cursor**

Use a loopback file server in this Go process. It removes the Wails asset hook from the video path, which is the slow part, and it fits the way the app already opens files from arbitrary folders.

WebView2 folder mapping is the closer match to `file:///`, and it is the fallback if a normal localhost server is still slow. It is the wrong first change: Wails 2.12 does not expose that API, and one hostname maps to one folder while the source file and the preview proxy live in different directories.

**Loopback server** (`http://127.0.0.1:<port>/…`)

- The video element uses Chromium’s normal HTTP stack, with keep-alive and range requests, instead of the Wails callback that opens the file in Go and sends `Cache-Control: no-cache`.
- Any opened path works, including a preview file under `%TEMP%`, through the registry you already have.
- The same URL works in the Wails window and in the browser during `wails dev`.
- The page and the video are different origins. Playback and seeking are fine. Reading pixels from the video in the page would be blocked; frame capture already goes through ffmpeg, so that does not matter.
- It is still HTTP. If WebView2’s media pipeline is slow for every HTTP URL, not only for the asset hook, this will not match LosslessCut. That is the signal to try folder mapping.

**WebView2 folder mapping** (`SetVirtualHostNameToFolderMapping`)

- The WebView2 runtime reads the disk itself, which is the same idea as `file:///`.
- No extra port, and the response does not pass through Go.
- Wails does not wrap the call, so the app has to reach the WebView2 controller after startup. That binding is fragile across Wails versions.
- Each hostname points at one directory. A file on the Desktop and a proxy in `%TEMP%` need two mappings, or the mapping has to change whenever the open file’s folder changes.
- The hostname exists only inside the WebView2 window, so the dev browser cannot play the file.
- Some WebView2 versions have been weak at range requests on these mappings. A broken range response makes seeking worse, not better.
